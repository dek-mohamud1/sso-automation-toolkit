# Domain Knowledge: SSO Automation Toolkit

## Overview

A browser-based internal tool for Florence Healthcare engineers that automates
SAML metadata parsing and SSO configuration. Engineers provide a metadata XML
URL or file, and the tool extracts all critical SSO values, surfaces certificate
expiration dates, parses claims/attributes, and generates a client-ready metadata
XML — across both Production and UAT environments.

## Business Context

Implementation and support engineers configure SSO/SAML integrations for clinical
trial sites. Each client provides metadata XML from their identity provider (IdP).
This tool eliminates manual XML parsing, reduces setup errors, and handles both
Production and UAT in one place — cutting time spent per integration roughly in half.

## Key Concepts

### SAML Metadata XML

Provided by the client's IdP as a URL or file upload. Contains all values needed
for SSO setup — Sign-In URL, Sign-Out URL, certificates, and claims.

### Auth0

Florence Healthcare's identity platform. The extracted metadata values are used
to configure Auth0 enterprise SSO connections for each client.

### Certificate + Expiration Date

The tool always extracts the latest X.509 signing certificate and displays its
expiration date so engineers can flag renewals before they cause outages.

### Claims and Attributes

User attributes passed in the SAML assertion (e.g. email, name). Parsed and
displayed for Auth0 attribute mapping.

### Generated Metadata XML

Output file generated by the tool containing Florence Healthcare's SP metadata,
formatted correctly for the client's IdP to consume — for both Prod and UAT.

## Business Rules

1. Input can be a metadata XML URL or a file upload — both must be supported.
2. Always extract the most current certificate, never an expired or secondary one.
3. Certificate expiration date must be clearly visible.
4. Claims and attributes must be parsed and displayed in a readable format.
5. Metadata XML must be generated for both Production and UAT environments.
6. All processing is client-side only — no client data sent to any external server.
7. Internal use only — not exposed to clients or the public.

## User Personas

### Implementation Engineer

- **Role:** Configures new client SSO integrations during onboarding
- **Goals:** Parse client metadata, extract all values, generate output metadata
  for both Prod and UAT without manual XML reading
- **Pain Points:** IdP formats vary, manual work is slow and error-prone, repeating
  the process for Prod and UAT doubles the effort

### Support Engineer

- **Role:** Troubleshoots broken or expiring SSO connections
- **Goals:** Quickly identify bad or expiring values from client metadata
- **Pain Points:** Missing certificate expirations before they cause outages,
  manual parsing during live incidents

## Compliance

- Client-side processing only — no PHI or credentials transmitted externally
- Internal Florence Healthcare tool only
- Follows internal security standards for browser-based tooling
